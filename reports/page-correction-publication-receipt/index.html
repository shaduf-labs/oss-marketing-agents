Did the approved page correction reach the public URL?

Approved ≠ deployed ≠ public ≠ indexed. Check one ordinary public URL before calling a correction live. A saved edit, successful build or Google live test answers a different question.

Evidence statusThis is a primary-documentation decision contract, not an observation of a customer page. The example below is wholly fictional. No authorized customer URL, CMS, repository, deploy, CDN log or Search Console property was available.

One-page receipt: what to retain

Choose a distinctive exact sentence from the approved copy. Then collect the narrow evidence for each stage. Keep unknown fields unknown rather than filling them from a deploy notice.

Source Markdown, built HTML and compressed response bytes need not hash alike. GitHub Pages publishing source · HTTP caching standard · Google URL Inspection

Run the manual check first

  1. Compare the approved artifact and marker with the saved source and deployment result. On GitHub Pages, a branch/folder or Actions artifact is configured as the publishing source and a workflow deploys the site. A successful deployment status supports the deploy stage only. Other CMSs need their own revision and release records. GitHub Pages deployment status API
  2. From outside the authoring preview, fetch the ordinary, unmodified public URL, follow redirects, and retain the final response and timestamp. Check status, final URL, exact text marker, canonical and robots directives.
  3. If geography, device, login or CDN edge can change copy, check the relevant authorized variants and state coverage. A cache-busting query or hard refresh can diagnose a stale path, but it is not the normal-URL receipt.

Age estimates a cached response's age; no Age header does not prove origin contact. Vary may select different stored responses. RFC 9111 permits fresh cache reuse and conditional revalidation. One fresh fetch does not prove every variant was purged. RFC 9111, sections 4–5

Google is a separate boundary

URL Inspection's default indexed view describes Google's most recently indexed version, not necessarily the current page. Its live test asks whether a page can likely be indexed; it does not prove inclusion, selected canonical or the intended copy served to users. The live test follows redirects but does not disclose the final URL it tested. An indexing request is not an inclusion guarantee. Independently inspect HTML robots, X-Robots-Tag and canonical signals in the public response; an HTML canonical is a preference, not a selection guarantee. URL Inspection · robots directives · canonical methods

This receipt concerns whether a correction was served. It does not establish traffic or causal search effects. The 20 October page-priority report covers what to diagnose before a content edit. If email or social already links to the page, retain the sent artifact, URL, timestamp and exposure record; fixing the page cannot retract a sent message or public post. See the 15 October channel-receipt report.

Do not add a monitor for one correction

Repeat the manual receipt for the one page. If many owned public URLs need recurring checks, a reviewed post-deploy script could fetch each final public URL and compare the approved marker, status and policy fields while keeping response receipts. Comparing only a source tree or build artifact remains a source/deploy check. No monitor project, executable, licence or data/network exposure was selected or audited here. Before choosing one, verify its exact version, licence, target permissions and outbound behavior, then test normal-final-URL and relevant-variant coverage. An alert is an exception signal, not approval, cache parity, Google indexation or ranking proof.

Still needed for a real decision: approved artifact and marker; authorized final URL; source and deploy identifiers; an independent public response with variant scope and headers; and Search Console access only if indexed state matters. Without them, this is a decision contract, not a claim that a customer page changed.
